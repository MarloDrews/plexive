# Writing an entry in ARCHITECTURE.md

THIS IS DELIVERED ON **READ**, so a session that opens ARCHITECTURE.md at any offset gets it and
a session that never opens the file does not. That is the same asymmetry `code-files.md` records
about itself, pointed the useful way here: the only session this rule is for is one with the file
open, and there is no slice of the file it can be read past.

WHY IT IS NOT IN THE FILE'S OWN HEADER, where two of these six clauses used to sit: an entry is
appended near the line it belongs beside, and a header 300 lines above it is not delivered by
reading there. The header now points at this file and states no clause of its own; if a clause
ever survives in both, one of them is wrong and nobody can tell which.

- An entry earns its line by what it RULES OUT or by where it POINTS: a constraint, a ban, a
  deliberate omission, a contract between two files, or the reason a thing is the way it is. It
  does not earn its line by describing what a file contains, because the file answers that better
  and the description drifts silently while the file moves underneath it. NONE OF THOSE FIVE
  IS VISIBLE IN ANY ONE FILE, which is the whole reason they are written down, and each is a
  thing a session would otherwise build, break or trim in good faith. THE FIVE ARE THIS ROLE'S
  OWN KINDS AND NOT A SENTENCE CARRIED OVER: the header of ARCHITECTURE.md named four until
  2026-09-03 and left out the reason a thing is the way it is, and a file whose role is
  cross-file constraints AND the reasons behind decisions cannot state a list that omits the
  reasons. Whoever shortens this list back to four is reversing that, not tidying it.
- A location claim earns its place when it says something THE TREE DOES NOT SAY. An entry that
  restates the path it is printed at, with or without an endpoint list beside it, earns nothing.
- A bare parameter, cap, clamp, default or list of fields earns its place only when the entry says
  something the code does not: why it is that number, what it deliberately excludes, or a contract
  with a named other file.
- An entry carrying neither a rule-out nor a pointer gets NO LINE AT ALL, name included. The
  section is not an index of the tree, and a file's absence from it says nothing about the file.
- THERE IS NO ONE-LINE-PER-ITEM RULE. It stood in three places and was retired as measurably
  false; measured 2026-09-03 over the 297 entries in `## FOLDER STRUCTURE`, the median entry is
  443 characters of prose and the longest is 7,139.
- SHORTENING AN ENTRY IS THE OPERATION THAT PRODUCES DEFECTS, not deleting one. The 2026-09-03
  pass dropped 43 entries net and every deletion was found sound by a session that had not written
  it, while its own defects all came from a partial deletion leaving a clause whose subject or
  antecedent had gone out from under it. Delete the line or leave it; a tidy-up is the dangerous
  edit.

"OR WHERE IT POINTS" IS LOAD-BEARING AND IS NOT TIDIED AWAY FOR BREVITY. Until 2026-09-01 the
section called itself a one-line-per-item map, and that phrase was the whole standing argument for
every location claim in it. Retiring the phrase removed the argument, so the pointer clause now
carries it, and a batch shortening that sentence for style would delete the case for a class of
content without touching one entry. Replacing it takes a decision, not an edit.
