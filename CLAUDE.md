# Plexive

Open source social media app that replaces doomscrolling with valuable content.

## Tech Stack
- Backend: Python FastAPI
- Frontend: Next.js
- Database: Supabase PostgreSQL (connection via `DATABASE_URL` in `backend/.env`)
- License: AGPL v3

## Content Model

## Git Workflow

`main` is protected by a ruleset: the `android-build`, `backend-checks` and `frontend-checks` status checks are required and force pushes are blocked. A commit therefore cannot be pushed straight to `main`, because a fresh commit has no check result yet.

Changes reach `main` this way: branch off `main`, push the branch, open a pull request, let the three checks go green on it, then merge. This is not a review requirement; the same person may open and merge the pull request.

All three run once per pull request, on the `pull_request` trigger. Pushing a branch on its own produces no run, so the checks appear only once the pull request exists.

The merge itself is a MERGE COMMIT, made with GitHub's "Merge pull request" button. Not a squash, not a rebase, and not a local `git merge` followed by a push: the ruleset requires a check to have reported on the commit, and a merge commit created locally has no check result, so the button is the only route. `git log --merges` is the record and shows the mechanism -- every merge commit here is authored by the person and committed by `GitHub <noreply@github.com>`. The title obeys the same conventional-commit rule as any other commit: `chore(merge): merge <branch> into main`. Dependabot's own pull requests keep the title Dependabot generates, which is already conventional, so they need no rewriting. That title is `build(deps): bump ...`, or `build(deps-dev): bump ...` when the package is a dev dependency -- NOT `chore(deps):`, which is what this note used to quote. The point of quoting it is that it is exact, so: every Dependabot pull request this repository has had is npm (#38-#42 in `mobile/`, #45-#48 and #50 in `frontend/`) and every one of them is `build(deps)` or `build(deps-dev)`. The pip and github-actions forms are unobserved here, since neither ecosystem has produced a pull request yet, so do not assume they match.

Branches are named `<type>/<short-kebab-description>`, with the type drawn from the commit-type vocabulary. In use, by frequency: `docs/`, `ci/`, `perf/`, `fix/`, `feat/`, `chore/`, `deps/`, `build/`, plus `spike/` and `integration/`. Those last two are naming prefixes and nothing more. They say what the branch is FOR -- `spike/` for work that may never merge, `integration/` for a branch that collects several changes before one merge -- and they exempt nothing: a merged `integration/` branch is deleted like any other, and the ancestry check below applies to every prefix without exception. `integration/facts-all` was merged and then deleted, which is the rule working, not a violation of it; the only branch alive on that basis today is `spike/static-analysis-toolchain`, which is NOT an ancestor of `main` and is unmerged rather than exempt. `deps/` is for a hand-assembled dependency batch; Dependabot names its own `dependabot/<ecosystem>/<path>/<package>-<version>` and those are not ours to name or to rename.

A merged branch is DELETED, remote and local, by whoever merged the pull request, as part of the same batch. Before deleting, confirm the branch is an ancestor of `main` rather than trusting the pull request's "Merged" badge: `git merge-base --is-ancestor <branch> origin/main`, or `git branch --merged origin/main` to list the safe ones in one go. The badge is not the same claim. It is equally green for a squash or rebase merge, where the branch's own commits are NOT on `main`; it stays green for a branch pushed to after the merge, which is then no longer contained; and it says nothing about the local branch, which is a separate ref. Ancestry is the only statement that the commits are actually there, which is why recent batches check it and why deleting on the badge alone is the thing this rule exists to prevent.

CONFIRM CHECK RESULTS AGAINST THE HEAD SHA, NOT AGAINST WHATEVER `watch` RETURNS. This sits here rather than in the tally because it is a step in the merge, not a story about one. `gh pr checks --watch` can report the PREVIOUS head's results as green -- measured 2026-08-28, complete with durations and job URLs, seconds after a push -- so a merge can be approved on evidence about a commit that is no longer the one being merged. The check that cannot be stale names the commit:

    SHA=$(git rev-parse HEAD)
    gh api "repos/:owner/:repo/commits/$SHA/check-runs" --paginate \
      --jq '.check_runs[] | select(.name=="android-build" or .name=="backend-checks" or .name=="frontend-checks") | "\(.name) \(.status) \(.conclusion) job \(.id)"'

Read the JOB IDS as well as the conclusions: identical ids across two different heads is the tell, and it is the only part of that output that distinguishes a fresh green from a stale one.

## CI Notes

The workflow uses `distribution: corretto` because `mobile-kmp/gradle/gradle-daemon-jvm.properties` pins `toolchainVendor=AMAZON`. Any other vendor makes Gradle ignore the installed JDK and download Corretto from foojay on every run. Changing that line means changing `.github/workflows/android-build.yml` too.

The `push` trigger is scoped to `branches: [main]` on purpose. Unscoped, it also fires on the branch behind a pull request, so one commit gets two runs reporting the same `android-build` check name and the required check resolves to whichever finishes last. Do not widen it to make branches build; branches build through their pull request. Keeping `main` is what seeds the Gradle dependency cache, since `setup-gradle` only writes the cache from the default branch, and a cold run takes about 3m25s against about 40s warm.

There are five workflow files. Three are gates, one per codebase, one job each: `android-build.yml`, `backend-checks.yml`, `frontend-checks.yml`. One job per codebase on purpose. The number of check names a person has to interpret on a pull request is the real budget, and three is what it will bear.

`codeql.yml` and `dependency-submission.yml` are the other two, and neither is a gate. Both are deliberately absent from the ruleset, so the required checks are still exactly those three, and they are the reason the sentence above says "three gates" rather than "three workflows".

`codeql.yml` breaks one of the patterns below on purpose: it runs a matrix, so it contributes two check names, `codeql (python)` and `codeql (javascript-typescript)`, neither of which is required. Its languages are `python` and `javascript-typescript`; `java-kotlin` is excluded because CodeQL cannot analyse Kotlin without a build -- `build-mode: none` is supported for Java and explicitly not for Kotlin, where it skips the code and emits a warning -- so covering `mobile-kmp/` would mean a second real Gradle build alongside `android-build.yml`. That is a separate decision, not an oversight.

It gained `push: branches: [main]` on 2026-08-27, so its triggers are now push-on-main plus `schedule:` plus `pull_request:`. This matters because code scanning tracks alerts against the DEFAULT BRANCH: the Security tab is populated by runs on `main`, and a pull request run reports on that pull request alone. Before the push trigger the baseline came from the weekly schedule alone, so a merge did not refresh the Security tab and the baseline could be up to a week stale. That was traded for one extra run per merge, deliberately and on the user's instruction, because Actions minutes are unmetered on a public repository and a stale baseline is the more expensive of the two. The schedule stays, but its job has changed: it is no longer what establishes the baseline, it is what keeps the analysis fresh against newly published CodeQL queries during a week with no merges.

Adding it also silenced a warning worth recording, because it will not appear again and someone reading old logs will meet it. While there was no `push:` trigger, `codeql-action/init` emitted `##[warning]1 issue was detected with this workflow: Please specify an on.push hook to analyze and see code scanning alerts from the default branch on the Security tab.` on EVERY run, once per matrix leg. It was a static lint on the workflow file, not a report that anything failed, and it was wrong in the narrow sense that scheduled runs did execute on `main` and their analyses were default-branch analyses. The real gap it pointed at was the latency described above.

`dependency-submission.yml` is the fifth, added 2026-08-27, and it runs `gradle/actions/dependency-submission@v4` over `mobile-kmp/` to close the Gradle dependency-graph gap described under Repository Security Settings. It is a separate workflow rather than a step in `android-build.yml`, for three reasons in order of weight. Permissions: submitting a snapshot needs `contents: write`, and folding it into `android-build` would hand write scope to the job that builds unreviewed pull request code, which runs `contents: read` today. Triggers: a snapshot describes the DEFAULT BRANCH, so this must run on `main` only, while `android-build` must run on pull requests; one file cannot hold both without one of them firing where it should not. Cost: the action runs its own Gradle invocation, and inside `android-build` that time would land on a required check, whereas a separate workflow runs in parallel and slows the gate by nothing. It also leaves `android-build`'s compile-task assertion alone, which parses that job's own `--console=plain` log and would otherwise have a second Gradle run's output to contend with. It never runs on `pull_request`, so it contributes no check name to any pull request, which is the strongest form of "not a gate" available.

First run on `main` under the new `push:` trigger, 2026-08-27, on the merge that added the trigger: 87 rules and 0 results for `javascript-typescript`, 43 rules and **1** result for `python`. That one result is the first entry the Security tab has ever had: `py/clear-text-logging-sensitive-data`, high, at `backend/seed.py:239`, where the seed script prints a generated admin password to stdout when `SEED_ADMIN_PASSWORD` is unset. It was deliberate code -- the message it printed said "Save this now" -- so it was a triage decision rather than a bug report. It was ACTED ON on 2026-08-28, and the finding is now the Security tab's only cleared entry. The measurement, put next to the claim: the push run on `main` for that merge (2c1bb53) reported `python` 43 rules and **0** results, against 43 rules and 1 result on the preceding main run (41bbd76); the alert moved to `fixed` at 2026-08-27T22:24:19Z and open code-scanning alerts are now 0. The RULE COUNT is the load-bearing half of that. 43 is the same count the run carried when it reported the finding, so the zero is those same 43 rules finding nothing rather than a smaller suite asking a smaller question -- which is the difference between a real result and a vacuous pass, and the same reason the first-run note above quotes its rule counts at all.

What was wrong with it was the destination, not the intent: an operator on a fresh database has to learn the password somehow, but stdout is redirected often enough (`| tee`, `> seed.log`, a scrollback that outlives the terminal) that the value landed in a file on disk. Relocating the output does not fix that and does not clear the rule either, which was checked against CodeQL's own sink definitions rather than guessed. `CleartextLoggingCustomizations.qll` models `print(...)` AND `sys.stdout.write` / `sys.stderr.write` as sinks, so printing to stderr instead changes nothing. `CleartextStorageCustomizations.qll` models a plain `open(path,"w").write(x)` as `FileWriteDataAsSink`, and `CleartextStorage.ql` is `@precision high` with a `security` tag, so it is in the same default suite this workflow runs -- writing the generated password into `backend/.env` would have traded `py/clear-text-logging-sensitive-data` for `py/clear-text-storage-sensitive-data` and cleared nothing.

There is therefore NO channel where the script reveals a generated secret and the tab still reads zero, and that is the scanner being right rather than being awkward: a generated secret has to go somewhere, and every somewhere is a copy in a place it should not be. So the script stopped generating and started asking. When `SEED_ADMIN_PASSWORD` is unset it reads one with `getpass.getpass()` plus a confirm entry, which does not echo; the cause is gone rather than the output moved, and there is nothing left to disclose. The no-terminal branch was also moved AHEAD of the reveal, which is a real bug the finding happened to expose: the `sys.stdin.isatty()` check used to sit after the print, so a non-interactive run disclosed the password and only then refused to continue. Nothing calls the script non-interactively -- `docs/SERVER.md:127` is a by-hand `sudo env ... python seed.py` whose env file already carries the variable, `tools/run_pipeline.{sh,ps1}` only echo the command as an instruction to the human, and `backend-checks.yml` only byte-compiles it -- so this broke no caller.

Worth recording because it is the argument for the push trigger, made by the trigger itself on its first run: the pull request run on the SAME commit reported 43 rules and 0 results for `python`, so the pull request leg did not surface this and the scheduled run would not have surfaced it for up to a week. The difference is scope, not luck -- a pull request analysis reports against that pull request, a default-branch analysis establishes the baseline -- and this is exactly the staleness the trigger was added to remove.

First run, 2026-08-27, on the pull request that added the file: 87 rules and 0 results for `javascript-typescript`, 43 rules and 0 results for `python`. Zero is the real number and not a vacuous pass -- GitHub's own `code-scanning/analyses` API reports the same two rule counts the in-workflow SARIF assertion did, and CodeQL hard-fails rather than passing quietly when it finds no code of a language it was asked for, so both databases finalized over real source. The default query suite is the high-precision security one, so this says nothing about the 88 ESLint errors, which are a different tool asking a different question.

No workflow has a `paths:` filter. A workflow skipped by a top-level `paths:` filter reports no status at all, and a required check that never reports blocks the pull request permanently. Actions minutes are unmetered here, so the saving would buy nothing anyway.

Every job sets `shell: bash` explicitly. The Linux default is `bash -e {0}`, without `pipefail`, which is how a piped failure becomes a green check; `shell: bash` is `bash --noprofile --norc -eo pipefail {0}`. This already bit the Android workflow once.

Every check asserts on a count, not only on an exit code, because all of them can pass having checked nothing: a loop that globs no files exits 0, `compileall` over a wrong path exits 0, `npm test` with no matching files exits 0 reporting `pass 0`. The counts are floors well below what was observed, not exact numbers: a route count or a test count moves with normal feature work, and a gate that reds during correct work is a gate that gets switched off. The floors that sit at their observed value (16 suite files, 40 frontend tests) only move down through a deliberate deletion, which is worth a deliberate edit here.

The backend suites run as a per-file subprocess loop, not `pytest tests`. 12 of the 16 suites execute their whole body at import and share one app instance, one in-memory rate limiter and the first module's temp SQLite file, so in one process they collide: pytest collects 92 of about 979 assertions and interrupts on 4 collection errors. The loop also runs every suite after one fails, so a second failure is not hidden behind the first.

The `backend-checks` suite loop hung three times, every time on `battle_test.py`, all three on 2026-08-27, and every time on a commit that touched no backend code. It is DIAGNOSED AND FIXED as of 2026-08-27; the cause was the test harness and not the server, and several of the notes below used to say the opposite. They are corrected in place rather than deleted, because the wrong inferences are the useful part of the record. Full workings: `docs/research/battle-hang-diagnosis-2026-08.md`.

One earlier observation is retired outright: "three for three it has also come straight after `arena_test.py` passed" carries no signal whatsoever. The suites run as separate processes over an alphabetical glob, so `arena_test.py` precedes `battle_test.py` in every single run, including the 22 that passed.

Rate, so the count is not read as a frequency: 25 runs of this workflow, 3 of them hangs. Note that the second and third are invisible in the Actions run list, because re-running a job overwrites the run's conclusion and it now reads `success`; the evidence is the log of the first attempt, not the run's status.

Every other thread is idle: two `anyio` worker threads parked in `queue.get`, three portal event loops parked in `selectors.select`. Nothing is spinning and nothing is deadlocked on a lock. The suite is simply blocked forever waiting for a WebSocket frame that never arrives.

`battle_test.py:124` is `fin_a = ws_a.receive_json()`, in the "both finish frames end the room" section that freezes ARCH-004. The sequence is: alice sends `finish`, bob receives `opponent_finish` (line 121, which had already passed), bob sends `finish`, and alice never receives hers.

THE INFERENCE DRAWN FROM THAT WAS WRONG, and this is the correction. The note here used to say that the second `finish` is sometimes not relayed to the player who finished first, blamed "a race between the first `finish` tearing the room down and the second one looking for somebody to relay to", called it a lead pointing at the M142 finish/teardown path, and moved the state machine from not implicated to implicated. The line number and the dump were right. Everything read off them was not. THE STATE MACHINE GOES BACK TO NOT IMPLICATED, on evidence rather than on absence of evidence: `battle.py:220-221` captures both the recipient and the battle id BEFORE the teardown pops at `:222-225`, inside the same single lock acquisition, and `manager.send` resolves the socket from `_sockets`, which `_teardown_room` never touches. There is no window in which the second `finish` loses its recipient. Driving the same app over in-process ASGI websockets on ONE event loop ran 500/500 clean, including the stale branch and back-to-back finishes, which bounds the server-side failure rate below roughly 6 in 1000.

The cause was the harness. `battle_test.py:34` constructed `TestClient(app)` and never entered it, and starlette only shares one portal when the client is entered, so EVERY `websocket_connect` got its own portal, its own event loop and its own thread -- those are the "three portal event loops parked in `selectors.select`" the dump itself reported. Bob's relay then ran on bob's loop and wrote into a stream owned by alice's loop, and anyio wakes that receiver through `loop.call_soon`, which unlike `call_soon_threadsafe` does not write the target loop's self-pipe. With alice's loop already parked in `select(None)` the frame is delivered and the loop is never woken. Not a lost message: a lost wakeup. Measured at 1 hang in 200 locally and 3 in 200 on the CI-pinned set, and made deterministic by delaying the second relay 50 ms (5/5 hangs, 0/30 after the fix). READ THOSE TWO NATURAL RATES AS SINGLE SAMPLES OF A RATE THAT MOVES WITH MACHINE LOAD, not as properties of the code: a later session on the same local set hit a natural hang on the third run of its first five, which is 1 in 5 rather than 1 in 200. The forced case is the measurement; the natural rates only establish that the window is small, real and variable, and CI's own 3-in-25 is a third sample from a third machine. The fix is one line, `stack.enter_context(client)`, and the same line in `chat_test.py`, which was exposed identically and hangs under the same forced delay at its own cross-loop read (`chat_test.py:154`). See the DEPLOYMENT INVARIANT section of ARCHITECTURE.md for the general rule this violated.

Starlette moved 1.2.1 -> 1.3.1 between the first two occurrences, and it is now CLEARED rather than merely unimplicated: the race reproduces on both, 3 hangs in 200 runs on the CI-pinned 1.3.1 and 1 in 200 on the local set, and the forced 50 ms repro hangs 5/5 on each. One caveat kept honest: the local environment is starlette 1.2.0, not the 1.2.1 named above, so 1.2.1 itself was never run. The versions either side of it behave identically, which is why this is stated as cleared. The `StarletteDeprecationWarning` about `httpx` is not a lead either, it is emitted at import on every run under 1.3.1 including passing ones, and is simply the last thing printed before the dump.

The re-run policy is inverted by the fix, so it is restated here rather than deleted. Re-running a red `battle_test.py` unchanged was the CORRECT response while the cause was unknown, unreproducible and believed to be in the server: the suite genuinely passed on the retry, and a merge could not wait on a fault nobody could reproduce. It is the WRONG response now. The known cause is gone, so a fresh hang or a red `battle_test.py` is a new fact and must be read, not retried -- and retrying actively destroys the evidence, since re-running a job overwrites the run's conclusion, which is exactly why the second and third occurrences are invisible in the Actions run list. Read the log of the first attempt: the suite now carries its own watchdog and prints a stack before it dies.

Each suite therefore runs under `timeout 300s`, and the job carries `timeout-minutes: 20`. THE DERIVATION OF THAT 300 s CHANGED ON 2026-08-28 AND IS RESTATED RATHER THAN LEFT DANGLING, because a constant whose stated reasoning names a deleted file is how the next person talks themselves into changing it. It was about 2.3x `thumbnails_test.py`'s 130 s, the slowest healthy suite; that suite left with the thumbnail render subsystem, the slowest healthy suite is now `arena_test.py` at about 29 s in CI, and 300 s is therefore about 10x rather than 2.3x. The 180 s watchdog below went from about 1.4x to about 6x the same figure. NEITHER IS LOWERED. Both exist to bound an unbounded hang rather than to bracket a slow run, so a larger multiple costs nothing and buys margin on a shared runner. The dangerous direction is down: a per-suite timeout that fires on a slow-but-healthy run converts a reliable gate into an unreliable one, which is the fastest way to get a gate switched off, and hosted runner speed is not ours to control. `timeout-minutes: 20` is the backstop for a hang outside the loop, in `pip install` or the boot check. It is about 5x the observed job duration, and it is deliberately loose enough that a suite can burn its full 300 s and the summary table still prints, because a job killed by `timeout-minutes` prints nothing and that table is the only thing that names the suite that hung.

The summary reports four statuses, not two, and the loop runs every remaining suite after any of them. `TIMEOUT` counts as a failure but is not reported as `FAIL`, because the two mean different things and the distinction is the only thing that makes a second occurrence recognisable as a pattern. `KILLED` splits the same way again: `timeout --kill-after` sends SIGKILL, but so does the kernel OOM killer, and both arrive as exit 137. Exit 137 is therefore read as a timeout only when the elapsed time is at least 90 percent of the limit, since `timeout` cannot fire before its own limit; below that it is `KILLED`, cause unknown, with OOM the likely one. The named candidate used to be `thumbnails_test.py`, which was image-heavy; it left on 2026-08-28 and no remaining suite is an obvious OOM risk, so this branch now flags a cause nobody has a suspect for, which is more reason to keep it distinct rather than less. Each suite's name is also printed before it is invoked, because its output is redirected to a file and dumped only on failure: without that line a hang leaves the live log completely silent, which is why the first 2026-08-27 hang could only be attributed to a suite by cancelling the run. The second one was attributed from the summary table without touching the run, so this part is load-bearing and is doing its job.

`battle_test.py`, `chat_test.py` and `arena_test.py` additionally carry their OWN 180 s watchdog, a `threading.Timer` that announces itself in one line, dumps every thread's stack and exits 1. This changes what a hang in those three looks like, deliberately: it self-terminates at 180 s and lands in the `FAIL` branch, NOT in `TIMEOUT` at 300 s. A stack is worth more than a label, and the announcement line is what makes the lost label harmless, since it says in the log that the suite hung rather than that a check failed. THE USEFUL HALF IS THE INVERSE: after this change, a 300 s `TIMEOUT` on battle, chat or arena means THE WATCHDOG ITSELF DID NOT FIRE -- a hang before its timer started, a wedged interpreter, a process that outlived `os._exit` -- which is a rarer and stranger event than a `FAIL`, and nobody would guess that without being told. The other 13 suites are untouched and still report `TIMEOUT` in the ordinary way.

The watchdog was proved rather than assumed, 2026-08-27, by dropping a frame the suite waits on (measured at 90 s, before the limit was raised to 180 s; only the number changed): the timer fired at 90 s (94 s wall clock), the exit code was 1 so the loop counts it as a failure rather than a pass, the announcement and a full all-thread stack naming the parked line both reached the log, and the 20 `ok:` lines printed before the hang were still there. That last one is the whole reason `flush=True` sits on the announcement: `os._exit` skips every cleanup path, and CI redirects each suite to a file where stdout is block-buffered, so without it the log would show a stack and nothing else. A healthy run under the same redirection prints nothing extra.

Where the 180 s comes from, since a bare number invites someone to trim it. THE BINDING CONSTRAINT IS LOCAL FALSE POSITIVES, NOT CI COST. In CI this watchdog earns very little: `timeout --signal=ABRT 300s` under `-X faulthandler` already produces the same all-thread stack, so all the watchdog does there is make it arrive sooner, and a hang burning 180 s instead of 90 s out of a 300 s per-suite budget and a 20-minute job ceiling is negligible. Its unique value is LOCAL, where none of that instrumentation runs -- and local is exactly where the margin is thin. 180 s is about 5.7x the worst healthy run measured: 31.5 s on a 12-core laptop deliberately oversubscribed with 12 concurrent test processes, against ~2.7 s for the same suite in CI. It was 90 s for one commit, which was only 2.9x that worst healthy run; raising it is strictly better on the axis that matters and irrelevant on the one that does not. The dangerous direction is DOWN, the same as for the 300 s: a watchdog that fires on a slow-but-healthy run is the same mistake as a per-suite timeout that does, and the diagnosis session made exactly that mistake once with a 20 s watchdog before raising it.

Every suite runs as `python -X faulthandler` and is aborted with `timeout --signal=ABRT`, not the default `SIGTERM`, so that a hang leaves a stack rather than silence. This was measured on the runner rather than assumed, in both directions. `-X faulthandler` only dumps on a FATAL signal, which is SIGSEGV/SIGFPE/SIGABRT/SIGBUS/SIGILL and NOT SIGTERM: with SIGTERM the flag prints nothing at all, so the signal had to change too, and the flag alone would have been a no-op that looked like a fix. The exit code does not change, because GNU `timeout` reports 124 for a timeout whatever signal it sent unless `--preserve-status`, so the classification above is untouched and the 137 branch still catches a suite that outlives ABRT. A timed-out suite now has its FULL log printed instead of the last 40 lines, because the dump is the evidence and tailing it would throw away the top of it.

The rejected alternative was `faulthandler.register(SIGTERM)` from a `sitecustomize.py` on `PYTHONPATH`, which needs no signal change and touches no test file. It dumps, but `register()` does not terminate, so the suite outlived its own dump and `--kill-after` SIGKILLed it: exit 137, landing in the `KILLED` branch that exists to flag a suspected OOM. Buying a traceback by making a timeout indistinguishable from an OOM is a bad trade. One cosmetic side effect remains: `timeout` prints `the monitored command dumped core`, and because `/proc/sys/kernel/core_pattern` pipes to `systemd-coredump` the kernel ignores `RLIMIT_CORE`, so a core is handed to systemd. Nothing is written into the workspace and the runner is ephemeral, so this costs nothing; `ulimit -c 0` is set anyway.

A BEFORE-NUMBER IS TAKEN BEFORE THE TREE IS TOUCHED, AND THE TREE MUST BE UNCHANGED FOR THE WHOLE TIME IT IS BEING MEASURED. This is a measurement rule, not a CI rule, and it sits here with the others because it is the same failure class. It was learned on 2026-08-28, during the thumbnail-removal batch: the backend suite loop was started to capture the before wall clock, and an edit deleting two classes from `app/schemas.py` landed while `thumbnails_test.py` was still running. That suite imports one of them, so it exited 1 after 131.3 s, and the total would have been reported as 267 s. Re-measured on a restored tree it was 130.3 s and exit 0, for a true baseline of 266.0 s.

What makes it worth a rule rather than a note is the SHAPE. The measurement did not error, the loop did not stop, and the number it produced was a plausible one -- 131.3 s against a true 130.3 s, well inside the noise anyone would accept. It was only caught because the exit code was checked as well as the duration, and the suite that changed was the one being timed. Had the edit hit a suite whose import it did not break, or had only the total been recorded, the wrong number would have been carried into the report and into the CI notes as fact. A measurement taken against a tree that is being edited is a checker that watches for a condition and reports its own failure as a result, which is the `## Rules` entry in a form the other thirteen instances do not cover: the tool was fine, the question was right, and the SUBJECT changed underneath it.

So: take every before-number first, in one pass, and do not begin editing until it has finished. Where that is impractical, record what the tree was at (`git rev-parse HEAD` plus a clean `git status --porcelain`) at both ends of the measurement and say so next to the number.

`tools/backup_supabase.sh`, added 2026-08-28. Supabase's free tier performs NO automatic backups, so this is the only copy.

THE AGE CHECK IS THE PART THAT MATTERS MORE THAN THE SCHEDULE. A forgotten backup is noticed the moment anyone looks; a scheduled one that has been failing for two months looks exactly like a working one until it is needed. `tools/check_backup_age.sh` reports the age of the newest manifest across FOUR situations with four exit codes, deliberately not merged: 0 current, 1 STALE, 2 NO BACKUPS AT ALL (the loudest, not the quietest), 3 current but never reached OneDrive. THRESHOLD 16 DAYS = 7 (weekly) + 7 (one occurrence lost outright, since StartWhenAvailable cannot fire on a machine that is off) + 2 (a weekend nobody would act in). The dangerous direction is DOWN, as with the 300 s and 180 s CI timeouts: a check that reds on a healthy-but-delayed backup gets switched off, and this one has no gate behind it. It reads METADATA ONLY -- Files On-Demand means reading a manifest would download it, while `stat` on a dehydrated placeholder returns the true mtime and size, measured.

THE SYNC STATE IS A RELIABLE NEGATIVE AND NOT A RELIABLE POSITIVE, and the distinction is the whole point. A file OneDrive has taken over carries FILE_ATTRIBUTE_REPARSE_POINT; one it has not touched does not, so ABSENCE proves no upload. PRESENCE proves nothing about the upload: measured across four sizes the bit appeared after 5 s (4 MB), 5 s (6 MB), 16 s (120 MB) and 44 s (800 MB), which as upload times would imply 6.4 to 145 Mbit/s -- RISING WITH FILE SIZE, which no fixed uplink does. So it marks a local placeholder conversion, not bytes reaching Microsoft. The only positive confirmation is opening onedrive.com, and `docs/SERVER.md` carries that as a step with its expected result. The shell's own `Verfügbarkeitsstatus` column was tried and rejected: COM-only, localised, and it returned an empty string on repeated reads of files it had answered correctly minutes earlier. The attribute is invisible to `stat`, `ls` and `attrib.exe` alike -- `attrib` prints `[A]` in both states -- so the check shells out to PowerShell and answers `n/a` where there is none, which is also what the Pi gets.

THIS WAS NOT HYPOTHETICAL. On 2026-08-28 the OneDrive sync client was NOT RUNNING on this laptop, so a file written into the OneDrive folder sat at attribute 32 with shell status "Synchronisierung ausstehend" for over eight minutes. Writing a backup there in that state succeeds, logs `rc=0`, reports age 0 -- and produces no offsite copy at all. That is exactly the shape this repository documents, in the one place whose absence ends the project, which is why state 3 exists rather than being folded into "OK".

A PREMISE MARLO SUPPLIED AS FACT, CORRECT IN GENERAL AND FALSE IN THE INSTANCE, and recorded as his because that is what makes it useful. The brief commissioning the schedule said: "OneDrive on Windows is a local folder that syncs, so the offsite copy is a property of where that path is. No cloud API, no credentials." Every clause is true about OneDrive. None of it was true about this machine, where the client was not running -- and the two backups already taken had never left the laptop. A premise that holds in general and fails in the instance is precisely what the measurement discipline here exists to catch, and it is why the answer came from writing a file and watching it rather than from reasoning about how OneDrive works.

THE CAUSE WAS ONE LAYER DOWN AND IS THE SAME SHAPE AGAIN, found by Marlo after the batch: OneDrive was DISABLED IN WINDOWS STARTUP APPS. The `HKCU\...\Run` entry was present and correct -- it was measured, and it is what made the client look configured -- but Windows keeps a SEPARATE ENABLE/DISABLE STATE that switches an entry off without removing it. So the registry read as right at exactly the place a person checks, and was overridden somewhere they do not. THE RUN KEY THEREFORE DOES NOT ESTABLISH THAT ONEDRIVE STARTS, and an earlier version of this paragraph implied it did. Three independent switches: the Run entry, Settings > Apps > Startup, and OneDrive's own "start when I sign in". The only trustworthy check is whether the PROCESS is running (`Get-Process OneDrive`) -- and note that `OneDrive.Sync.Service.exe` ran throughout while syncing nothing, so it is `OneDrive.exe` that matters. Full form, with the commands: docs/SERVER.md under "Wo die Backups liegen".

WHICH LEAVES ONE LINK NOTHING HERE CAN OBSERVE. A backup written while the client is down stays local until the client next starts; if it never starts, the file never leaves. The age check reports state 3 rather than OK, so it DOES catch this -- but only when somebody looks. A running sync client is what completes the chain, and no gate, no check and no scheduled task can see it.

THE LAPTOP IS THE PRIMARY HOST, NOT THE PI, and the reason is not convenience. The Pi is one device with one SD card at home and is already recorded as a single point of failure, so writing the only off-platform copy onto it moves the risk rather than removing it. Running it on the Pi and copying it off afterwards works and is the version people stop doing after the third time. The Pi remains the documented fallback: the script is bash and runs there unchanged.

THE MANIFEST IS THE PART THAT PAYS FOR ITSELF. A dump is worth something only if somebody restores it; the manifest is worth something the moment it exists, because it is the first written record anyone has kept of what production contains -- row counts per table, RLS state, policy list. It is printed LAST, after the not-covered block. Manifests are timestamped, nothing overwrites, and they must not be pruned: the sequence is a schema and growth history nobody is otherwise keeping.

Three documented ways to produce a backup that does not restore, all three handled in the script's own output rather than only in a document: storage OBJECTS are in no PostgreSQL dump and are backed up by no Supabase tier (only `storage.objects` metadata rows are, and the script prints that count so the number of dangling image references is visible); RLS is captured in the dump but re-enabling it on restore requires table ownership, so a restore under a non-owner role can come back with RLS OFF and still report success; and roles and their passwords need a separate `pg_dumpall --roles-only`.

THE ROUND TRIP IS VERIFIED, and the honest form of the claim is the whole claim: VERIFIED AGAINST A LOCAL POSTGRESQL 17.11, NON-SUPERUSER RESTORE, 2026-08-28 -- not verified against Supabase. Fixture of 6 tables and 92 rows with RLS plus a policy on one: dump, drop, recreate, restore returned row counts IDENTICAL to the manifest across all 6, with RLS and the policy back. The restoring role had `rolsuper` false ON PURPOSE. A SUPERUSER RESTORE WOULD HAVE ESTABLISHED ALMOST NOTHING, because superusers bypass the ownership check entirely, so a green result would have been equally consistent with "ownership was correct" and "ownership was never checked" -- a vacuous pass in its most convincing form, since it looks like a proof.

THE NON-OWNER HALF WAS MEASURED TOO, in the Supabase role shape (`rolsuper` false, `rolbypassrls` true, which is what Supabase's `postgres` reports). A table the restoring role does not own comes back with RLS OFF, no policy and no rows, while the control table it does own comes back intact in the same run. HOW LOUDLY THAT HAPPENS DEPENDS ENTIRELY ON THE RESTORE COMMAND, and this is the operational half: `pg_restore` prints every failure with its exact statement and EXITS 1; `psql -f` on the plain-SQL companion EXITS 0 with the errors only on stderr; `psql -v ON_ERROR_STOP=1 -f` exits 3. So "comes back with RLS off and still reports success" is real, but it is a property of the PLAIN-SQL PATH WITHOUT `ON_ERROR_STOP`, not of restoring in general.

WHICH HALF APPLIES TO PLEXIVE, since the two answers differ per schema and nobody should have to derive it under pressure: `public.*` -- every table Plexive owns -- is the FIRST case, because Supabase's `postgres` owns those, so a restore reapplies RLS and the counts match. `storage.*` and `auth.*` are the SECOND case, owned by `supabase_storage_admin` and `supabase_auth_admin`, so RLS and policies there come back OFF and the rows may not load at all.

SO, AFTER ANY REAL RESTORE, IN THIS ORDER: restore with `pg_restore` or `psql -v ON_ERROR_STOP=1` and never bare `psql -f`; read the exit code; compare `pg_tables.rowsecurity` and `pg_policies` against the manifest; then compare row counts. RLS before rows, because a restore missing rows is obvious and a restore missing RLS is not.

A ROLE THAT IS NEITHER SUPERUSER, `BYPASSRLS`, NOR THE TABLE'S OWNER CANNOT BACK THAT TABLE UP AT ALL. pg_dump issues every COPY with `row_security = off` and PostgreSQL then ERRORS rather than dumping a visible subset, aborting part-way and leaving a truncated file that looks like a backup. The script now refuses first and names the blocking tables. Supabase's `postgres` has `rolbypassrls` true, measured in the SQL editor, so this does not bite production today -- but that is a property of Supabase's current role configuration and not a guarantee.

`pg_dump` must match the server's MAJOR version. Older than the server it refuses outright; newer than the server produces a dump that can fail to restore back into it. Establish the server version first (`psql "$DATABASE_URL" -tAc "show server_version"`), then install that major.

A CORRECTION TO A BORROWED ASSUMPTION, because several documents would get this wrong the same way. **Plexive does not use Supabase Auth.** Accounts live in `public.users` with a bcrypt `password_hash` (`app/models.py:162-230`) and a self-issued HS256 JWT (`app/auth.py`); Google sign-in writes `public.users.google_sub`, not `auth.users`. So the usual Supabase warning that `pg_dump --schema=public` loses every account does NOT apply here -- a public-schema dump would in fact contain them. The script still dumps every schema the role can read, because measuring which schema holds anything beats assuming it, and the manifest's per-schema row counts settle it on the first real run. Read a low or zero `auth.users` count as the normal state, not as a missing backup.

First submission, 2026-08-27, on the merge that added the workflow: the SBOM went from 1268 packages and 0 Maven coordinates to 1965 packages and 696 Maven coordinates. The ecosystem split is now 1189 npm, 696 maven, 71 pypi, 8 githubactions. That count is the evidence the thing works, and it is what to re-read if anyone doubts it later; the workflow going green is not the same claim, because a Gradle build that resolved nothing would also go green.

What it buys beyond the coordinates arrived within the hour, and it is the reason this gap was worth closing rather than merely worth naming. Alerts are raised against coordinates, so once the coordinates existed `mobile-kmp/` went from 0 alerts to 50: 1 critical, 21 high, 26 medium, 2 low. Repository-wide open alerts went 13 -> 63. ## Closed Beta

Closed 2026-08-28. The product had been live on a public domain with open registration and no terms of service, no privacy notice, no reporting mechanism and no imprint. Nobody came to harm, but an open sign-up form is the one state in which a problem can be created from outside, so the door was shut first and the documents come later. Invite codes are a SEPARATE job and deliberately do not exist yet: this closes the door, it does not issue keys.

Measured before the change, anonymously, with `tools/probe_public_surface.sh`: 29 of 38 paths answered 200 with real content to a caller holding nothing. That included `/openapi.json` (55602 bytes), `/docs`, `/redoc`, the whole feed, any post by id, any profile, search, and the entire Net graph.

THE TWO HALVES ARE NOT EQUAL PARTNERS, and this is the thing to understand before touching either. The frontend holds NO application content. Every `page.tsx` is a client component, there are zero server-side API calls, no service token and no forwarded token; `plexive.org` ships a prerendered empty shell and the browser fetches everything from `api.plexive.org` directly. So **the backend gate is what closed the product**. The web gate covers a shell. Anyone reasoning about "is it closed" should reason about the API.

`api.plexive.org` is closed by `ClosedBetaMiddleware` in `backend/app/main.py`, a pure-ASGI layer keyed on `CLOSED_BETA=1`. Cloudflare Access was rejected on architecture rather than taste: the browser calls the API cross-origin, and Access answers an unauthenticated request with a redirect to its own login page, which an XHR cannot follow and CORS rejects; a service token would have to ship inside the public bundle. The middleware needs zero client change, because every client already sends `Authorization: Bearer`.

`plexive.org` is closed by HTTP Basic auth in `frontend/src/proxy.ts`. Vercel could not do it, and this was checked rather than assumed because it is the kind of thing that gets re-litigated: Password Protection is Enterprise or a $150/month Pro add-on, and Vercel Authentication on Hobby is "Standard Protection" scope, which the docs say explicitly leaves the production domain publicly accessible. The scope that would cover `plexive.org` is Pro/Enterprise. There is no Hobby-plan gate for a production domain.

Two file-name traps, both of which produce a gate that silently does not exist. The Next 16 convention is `proxy.ts`, NOT `middleware.ts`, which was deprecated and renamed in v16.0.0. And `proxy.ts` exports NO `config.matcher`: without one it runs on every request including `/_next/static`, `/_next/image` and `public/`, whereas the negative-lookahead matcher everyone copies excludes exactly those and leaves the shell, its JS and its CSS readable. Both were verified from outside, not reasoned about.

Deliberately still open, each for a stated reason: `GET /health` (a monitor needs it; 15 bytes, no application content), `POST /api/auth/login` and `POST /api/auth/google` (existing accounts must be able to sign in, or the beta is closed to its own testers), and `OPTIONS` preflight (a browser sends it precisely to ask whether it may send credentials). `/openapi.json`, `/docs` and `/redoc` are NOT exempt: the routes are removed outright, so they are 404 even with a valid token.

THE WEBSOCKET SCOPE PASSES THROUGH THE GATE UNTOUCHED, and this looks like a hole and is not. The three sockets carry no `Authorization` header at all -- the token arrives in the first frame, on purpose, so it cannot reach an access log. A header check would therefore reject EVERY socket and break battle, arena and chat silently, which is the exact quiet breakage a gate in front of a tunnel is known for. They are already closed by `app/ws_security.py`: TLS gate, per-IP handshake throttle, a 32-socket pre-auth cap, first-frame JWT plus `token_version`, and per-frame revalidation. Measured anonymously through the tunnel with `tools/probe_websocket.py`: all three upgrade to 101, send no content, and CLOSE at ~10.25s with code 4401. A 101 on these paths is not a leak; a content frame would be, and so would a socket that stayed open, because that holds a pre-auth slot.

Registration is closed TWICE, by two mechanisms that are independent on purpose. `/api/auth/register` is not in the exempt list, so an anonymous attempt never reaches the handler (401 from the gate); past the gate the handler itself returns 403. The second one is what matters later: reopening the gate must not silently reopen sign-up, so those stay two decisions. `/api/auth/google` is split -- its sign-in branches stay open and only the brand-new-visitor branch 403s, making it "sign in but never register".

`CLOSED_BETA` is read at import, so a forgotten variable on the Pi means the gate silently does not exist, and open is the state this fixes. The backend therefore ANNOUNCES ITSELF at startup in both directions (`[closed-beta] gate ON` / `gate OFF`), so `journalctl -u deepscroll-backend | grep closed-beta` answers "is it actually on" without anyone remembering to probe from outside. It is deliberately NOT fail-closed: refusing to boot over a missing optional flag is a worse failure than the one it guards. The frontend gate is the opposite and DOES fail closed, because there an unset variable only shows a password box, while a typo in a Vercel variable name would otherwise reopen the site silently.

THE GATE LOCKS THE OWNER OUT OF THEIR OWN ACCOUNT SETTINGS, and this was found the hard way on the day it went up. Changing a password happens in the web app; the web app is behind the Basic prompt; so between the API closing and the Vercel credentials being set, the password could not be changed at all. It surfaced as something worse than an inconvenience: the owner believed a password change had revoked a token that was still live, and only a measurement caught it (`/api/auth/me` answered 200, and the token still carried `ver: 0`, so `token_version` had never bumped). Anyone who needs to reach an account setting from behind the gate meets the same trap, and the same shape applies to any other setting only reachable through the gated UI. The way round it is the API directly: `PATCH /api/auth/me` with a bearer token bumps `token_version` and returns a freshly minted one in the same response, so the change can be made without the web app. Worth remembering before assuming a credential is dead because the usual route to killing it was tried.

THE BETA PASSWORD CONTAINS A NON-ASCII CHARACTER, and this is a KNOWN CONDITION rather than something to fix. It carries a EURO SIGN, which ISO-8859-1 cannot encode at all. Chrome sends it correctly because it honours the `charset="UTF-8"` on the challenge, and that covers most testers -- verified end to end in a real browser, 10 of 10 checks. A client that IGNORES that charset cannot send this password even in principle, which is not a theoretical worry: `curl -u` on this Windows machine answered 401 with the correct credentials, while the identical pair passed as an explicit base64 `Authorization` header. Two clients, same password, different answers.

WHERE THE CREDENTIALS THEMSELVES LIVE, since the paragraph above is aimed at someone who needs to try them: the username is `beta`, and the password is held OUTSIDE this repository. Nothing in the tree contains it and nothing in the tree should -- not this file, not `.env.example`, not the Vercel config committed here. Ask for it rather than searching for it; a search will turn up nothing and that is the intended state, not a sign it was lost.

WHAT THAT IS FOR: if a tester ever reports the prompt rejecting credentials they are certain are right, ENCODING IS THE FIRST THING TO CHECK, not the last. Everything about that report will point at a wrong password, a typo or a broken gate, and all three will be wrong. Ask what client they used before asking them to retype anything. This is written down to turn a confusing report into a one-minute answer.

WHAT THE ANDROID APP ACTUALLY NEEDS, recorded because "closing the API breaks the Android app" was the first summary and it is misleading. The network layer needs NOTHING: `NetworkModule.kt:64-88` installs a `sessionAuth` Ktor plugin that sets `Authorization: Bearer` on every outgoing request except the three session-establishing ones, and `FeedRepository` takes that same injected client, so `GET /api/feed` already carries a token whenever one is stored. Signed-in users are therefore unaffected by the gate. There is no token-wipe loop either, since `NetworkModule.kt:83-85` clears only when a token was actually sent, and a signed-out client stored none. What breaks is ONE UI ASSUMPTION: `FeedRoot.kt:48` shows the feed regardless of token state, so a signed-out user now meets a 401 where a feed used to be, and that screen needs to send them to `LoginScreen` instead. That is the whole follow-up. It was left undone deliberately -- changing how a client authenticates is a change to authentication, which was out of scope for a batch that put a door in front of what exists.

A DECISION THAT WAS MADE HERE, not a side effect, and it needs to be re-made rather than allowed to lapse: **the gate removed publicly readable post URLs.** Fifteen endpoints took an optional viewer and answered anonymously; they no longer do, so a post link now shows a stranger nothing. TikTok is the intended growth channel, which makes a publicly shareable post URL a plausible product requirement. When the gate lifts, whether those URLs come back is a PRODUCT DECISION and not a default. Lifting `CLOSED_BETA` would restore all fifteen at once, silently, because that is what the flag does -- and nobody would have chosen it.

## Local Tooling

`grep -c $'\r'` DOES NOT COUNT CARRIAGE RETURNS. It counts matching LINES, so on a file where every line ends CRLF it returns the line count, and on a file with none it returns 0 -- both of which look like a correct answer. Use a byte count instead, which cannot lie: compare `git cat-file blob :<file> | wc -c` against the working tree's `wc -c`, or count `\r` directly (`python -c "print(open(f,'rb').read().count(b'\r'))"`). Relevant here because `core.autocrlf=true` is set system-wide, so a file git CHECKED OUT is CRLF in the working tree while its blob is LF, and a file just written by an editor is whatever the editor wrote until git next touches it. Any claim about a file's line endings therefore has to say WHICH of the three it is about, and for the question that usually matters -- what a Linux host receives -- the answer is the index, which is LF. See the fourteenth occurrence above.

`psql.exe` ON WINDOWS ENDS EVERY ROW WITH CRLF, and this is a different CRLF trap from the one above rather than the same one restated. It bit `tools/backup_supabase.sh`: `$((TOTAL_ROWS + n))` on a captured `41\r` is a bash ARITHMETIC SYNTAX ERROR, the row total stayed 0, and the script FATAL'd at its own floor on every Windows run -- so the laptop, which that script names as its PRIMARY host, could never have produced a dump at all. What makes it hard to spot is that command substitution strips only the TRAILING newline, so a SINGLE-ROW capture loses its `\r` and works fine while a MULTI-ROW capture keeps one on every line but the last. A one-value probe therefore passes and the real query fails. Every psql capture in that script now pipes through `tr -d '\r'`, and the row-count query additionally sets `row_security=off` through PGOPTIONS rather than an inline `set`, because psql echoes the SET command tag as a row and it landed in the manifest's own table listing.

A `pgpass.conf` THAT IS SILENTLY IGNORED PRODUCES THE SAME PROMPT AS NO `pgpass.conf` AT ALL, which is the whole difficulty: the failure mode of a badly written one is indistinguishable from not having written one. Local PostgreSQL 17.11 here has `scram-sha-256` on every line of `pg_hba.conf`, so `psql` with no stored password PROMPTS -- and a prompt in a non-interactive tool call is a HANG, not an error, which is how it presents. The file goes at `%APPDATA%\postgresql\pgpass.conf`, one line, `localhost:5432:*:postgres:<password>`. Two ways to write it that look fine and are not: `notepad` appends `.txt` to the name, and PowerShell's default redirection writes UTF-16 -- libpq accepts neither and reports nothing either way. Use `Set-Content -Encoding ASCII`. Verify it by RUNNING a query and seeing no prompt, not by reading the file back. psycopg2 uses libpq too, so the same file serves `alembic` and `scripts/schema_diff.py` without a password in any URL. The password itself is `postgres`, the EnterpriseDB installer default that winget accepted silently without ever prompting: THERE IS NO SECRET BEING PROTECTED HERE, and a future reader finding this file should not assume otherwise. It exists so psql does not hang.

`jq` is NOT installed on this machine and is not on PATH: a bare `jq` in a pipeline fails with `command not found`. `gh api --jq`, `gh pr checks --jq` and `gh pr list --jq` all work, because `gh` carries its own jq implementation and never shells out to the binary. So anything reading the GitHub API uses `gh`'s built-in, and anything else that wants jq does without it.

The workflows' bare `jq` is correct and stays, but the reason is narrower than "it works in CI": it is a property of the `ubuntu-24.04` runner IMAGE, not of this repository, and that image is version-pinned here precisely because image contents move. There are exactly two such uses, both in `codeql.yml`, in the `Assert the analysis ran queries` step. Checked rather than assumed, and they fail loudly: `rules=$(jq ...)` is a plain assignment whose exit status IS the command substitution's, so under the `-eo pipefail` that `shell: bash` sets, a missing or erroring `jq` aborts the step at 127 -- verified by running it. Malformed input is caught too, because the `// 0` fallback yields `0` and the `[ "$rules" -lt 1 ]` floor then fails the step. One narrow hole exists and is left alone: if `rules` were ever NON-NUMERIC, `[ "$rules" -lt 1 ]` errors and returns 2, `set -e` exempts a test inside an `if` condition, and the step goes GREEN having asserted nothing -- also verified by running it. jq's `// 0` makes that unreachable today, and the step is not a gate: `codeql.yml` contributes `codeql (python)` and `codeql (javascript-typescript)`, neither of which is in the ruleset, whose required checks are still exactly `android-build`, `backend-checks` and `frontend-checks`. So the size of the exposure is one non-required assertion, and fixing it is a separate decision.

A second local-only divergence, found while verifying the `seed.py` change on 2026-08-28 and worth knowing before anyone tries to test a no-terminal code path here. On Windows, `sys.stdin.isatty()` returns **True** for `NUL`, which is what Git Bash turns `< /dev/null` into, because `NUL` is a character device and the CRT's `_isatty` answers for character devices rather than for terminals. Measured: `< /dev/null` gives `True`, a pipe gives `False`, a regular file gives `False`. Linux answers correctly in all three, so the Pi and the runners are unaffected -- this is purely a local testing trap, and the shape of it is that a guard which is correct in production looks broken on this laptop. Use a PIPE, not `< /dev/null`, to drive a non-interactive path here. Note also that `getpass.getpass()` on Windows reads the CONSOLE rather than stdin, so redirecting stdin does not make it raise `EOFError`; it just waits.

A third local divergence, and this one reaches anybody who clones on Windows. `core.autocrlf=true` is set in the SYSTEM gitconfig here (`C:/Program Files/Git/etc/gitconfig`, so it is not this repository's setting and not visible in `.git/config`), and until 2026-08-28 the repository had no `.gitattributes` to counter it. Every checkout therefore rewrote text files CRLF, which is harmless for everything except `.claude/skills/**/SKILL.md`, where it stops the frontmatter description from resolving and leaves the skill unmatchable. `.gitattributes` now pins that one pattern to `eol=lf` and nothing else, so the rest of the tree still converts -- measured in a clone at `autocrlf=true`: SKILL.md 0 CRLF pairs, CLAUDE.md 183.

It carries a trap worth knowing before anyone tests a `.gitattributes` change here, because it produced a checker that could not fail. Renaming `.gitattributes` out of the way and re-running `git checkout` does NOT remove the attribute: checkout reads attributes from the INDEX, not from the working tree, so a committed `.gitattributes` keeps applying to a file whose working copy has been moved aside. The first attempt at the negative half of the proof did exactly that, reported LF, and would have read as "the rule does nothing" when the rule was simply never absent. The valid test is a clone that does not contain the commit.

THE OCCURRENCES BEHIND THE `## Rules` ENTRY that a step watching for a condition reports its own failure. Nineteen have appeared in these notes now, and THEY ARE NOT ALL THE SAME SHAPE: eighteen are the recurring one, a checker that PASSES WHEN IT SHOULD FAIL, and the NINETEENTH is its INVERSE. It is set out at the end and kept distinct on purpose, because filing it under the other eighteen would lose the only thing that makes it worth recording. The eighteen are why it is written down as a rule rather than as another incident, and it applies just as much to a loop run by hand for five minutes as to a workflow -- it is already why every CI guard here asserts on a COUNT rather than on an exit code. Four of them are kept here, picked because they are the least alike. The THIRTEENTH is the most dangerous and is set out under Content Methodology above: a search whose glob could not see the file types that referenced its target, where no gate existed to be vacuous in the first place, so all three required checks would have stayed green over a dead pipeline.

The one that earned it, where the tool was broken: a monitor polling the three required checks piped `gh pr checks` through the external `jq`, `jq` was absent, every iteration produced empty output, and the loop reported "not green yet" for five minutes while all three checks had already passed. Nothing errored anywhere a person could see.

The one where nothing was broken at all: `gh api repos/:owner/:repo/dependabot/alerts` without `--paginate` returns the FIRST PAGE and stops, so a filter looking for anything past it prints nothing and reads exactly like a clean bill of health. Measured 2026-08-28: `--jq 'length'` gives 30 without the flag and 77 with it. The command was correct, `gh` exited 0, and the answer was still wrong, which is the half of the rule a broken-tool example cannot show. `docs/research/mobile-kmp-alert-triage-2026-08.md:64` passes `--paginate` for this reason, and the same document's guards defeat the same shape again, where a grep against an unresolved Gradle configuration would have read exactly like a clean bill of health.

The sharpest one, 2026-08-28, because it happened INSIDE the batch whose entire purpose was finding open doors. `tools/probe_public_surface.sh` took its account name from `${USERNAME:-Marlo}`. `USERNAME` is already set by Windows to the OS login, so the probe silently asked about `marlo` instead of `Marlo` and reported **404 for four profile endpoints that were in fact wide open**. Nothing errored, `curl` exited 0, and a 404 reads as reassuring -- a checker that reported CLOSED because it asked the wrong question, inside a script written to find things that were open. The variable is now `PLEXIVE_USER` and the reason is written into the file, but the occurrence is what belongs here: neither a broken tool nor a correct-command-wrong-answer, but a correct command asking about the WRONG SUBJECT, a third shape the first two examples cannot show.

THE FOURTEENTH, 2026-08-28, is a NEW VARIANT and the reason the tally moved rather than the rule being restated. Every one of the other thirteen was a checker producing an EMPTY result that read as a clean bill of health. This one produced a PLAUSIBLE NON-EMPTY NUMBER. Counting CRLF line endings with `grep -c $'\r'`, the pattern matched every line rather than the carriage returns, so the command returned the FILE'S LINE COUNT -- 144 for a 144-line script, 309 for a 309-line one. Those are exactly the numbers a real CRLF count would produce for a fully-CRLF file, so nothing looked wrong. WORSE, AND THIS IS WHY IT WAS BELIEVED: for the files git had checked out the broken measure was ACTUALLY CORRECT. `tools/probe_public_surface.sh` is 144 lines and really does carry 144 carriage returns, so the number agreed with the truth. It diverged only on the files written during the batch, which were LF -- `tools/backup_supabase.sh` reported 309 and holds 0. A measure that is right wherever you happen to check it first and wrong exactly where the question is new.

THE FIFTEENTH, SIXTEENTH AND SEVENTEENTH all arrived on 2026-08-28, in the batch that verified the backup round trip, and all three were committed BY VERIFICATION CODE rather than found by it. That is the part worth keeping: the rule is not about other people's checkers.

THE FIFTEENTH is a new variant -- A COMPARISON OF TWO ABSENCES REPORTED AS EQUALITY. The harness comparing manifest row counts against restored row counts ended in `diff -q`, and `diff` reports two EMPTY files as identical. Every stage of the run had failed, no manifest existed and no database had been restored, and the final line read `ROW COUNT COMPARISON: IDENTICAL`. Distinct from the other sixteen because neither list was wrong: both were simply absent, and absence compared equal. Fixed with a table-count floor (6 and 2 for the two phases) checked BEFORE the diff, and proven on identical input: old code says IDENTICAL, new code says COMPARISON INVALID and exits 1.

THE SIXTEENTH is the dangerous one and has no precedent in the other sixteen: A GUARD THAT FIRED CORRECTLY AND NAMED THE WRONG CAUSE. Four role assertions compared psql output against `t`/`f`, but `::text` on a boolean renders `true`/`false`, so every comparison failed and the first `die()` won. It reported "cannot SET ROLE" when SET ROLE was fine and the real gap was a missing BYPASSRLS. A guard that misdiagnoses is worse than one that stays quiet, because it sends somebody to fix what was never broken while the actual fault survives, and it does it with the authority of a check that just fired. WHAT SAVED IT IS A DESIGN RULE WORTH STATING GENERALLY: AN ASSERTION PRINTS WHAT IT MEASURED, NOT ONLY ITS VERDICT. The runner printed the measured value beside the required one, and a visible `true` next to "cannot SET ROLE" is a contradiction nobody can read past.

THE SEVENTEENTH shares the FOURTEENTH's shape -- a plausible wrong number rather than an empty one -- and is recorded separately because of where the number LANDED. `tools/backup_supabase.sh` counted rows without `row_security = off`, so for a table with RLS that the connecting role does not own it reported 0 for a table holding 6. Not an error, not an empty result: a small plausible integer, for a table anybody would assume was empty. The fourteenth's wrong number was read once and discarded; this one was written into the MANIFEST, the artefact whose entire purpose is to be compared against after a restore. A wrong number that persists into the record is worse than one that is merely read, because the comparison it corrupts happens later, by someone who was not there.

THE EIGHTEENTH, 2026-08-28, is in the tooling used to confirm EVERY MERGE in this project, which is what makes it worth more than the incident. `gh pr checks --watch --required` reported all three checks GREEN, with durations and job URLs, immediately after a new commit was pushed. Those were the results for the PREVIOUS head. Querying the new head SHA directly showed all three `in_progress` under DIFFERENT job ids. THE RIGHT ANSWER TO THE WRONG QUESTION, and indistinguishable from the right answer to the right one -- the same shape as the fifteenth, where a comparison of two absences reported equality, except that here the reassuring output was not even wrong, it was about a different commit. It surfaced only because the job ids were recognisably the ones seen minutes earlier; had the previous head's runs been slower, or the ids not been looked at, a merge would have proceeded on evidence about a commit that was no longer the one being merged.

THAT DEFECT CLASS IS NOT CHEAPLY GATEABLE, and the conclusion is to say so rather than to add a check. Nothing gates `tools/` -- the file-count and ruff floors are scoped to `backend/` -- but the honest finding is not "tools/ needs a gate". The CRLF arithmetic bug below was measured against the two checks anyone would reach for, and BOTH ARE GREEN ON THE BROKEN SCRIPT: `bash -n` exits 0, because `$((TOTAL + 41\r))` fails at RUNTIME rather than at parse time; and RUNNING it also exits 0, printing the arithmetic error to stderr and carrying on with the total left at 0. A syntax gate and a smoke-run gate would both have passed. What actually caught it was the script's own row-count FLOOR, which is a count assertion against a live database -- so surfacing this needed a real PostgreSQL and a real run, which is what the batch did. Adding a green check here would have been another instance of this same rule, not a fix for the thirteenth.

THE NINETEENTH, 2026-08-28, RUNS THE OTHER WAY, AND MUST NOT BE FILED WITH THE REST. Every one of the previous eighteen is a check that passes when it should fail; the reassuring output is the wrong one, and the rule exists because that is invisible. This one FAILS WHEN IT SHOULD PASS. It is arguably worse over time, and the reasoning is already written next to the 300 s and 180 s timeouts in the CI notes: a checker that reds on correct work teaches people to ignore red, and an ignored red is how a real failure gets waved through later. A vacuous pass costs you one missed defect; a checker that cries wolf costs you the checker, and then every defect after it.

Two instances, both in the batch that added the backup schedule, both committed by verification code rather than found by it. FIRST, an assertion failed while the condition it tested was TRUE: `bash tools/check_backup_age.sh | grep -q "..."` under `set -o pipefail` returns **141**, because `grep -q` exits at the first match, the producer takes SIGPIPE, and `pipefail` promotes that to the pipeline's status. It read as a genuine failure of the script under test, and the script was correct. Measured rather than reasoned: the CONDITION form gives rc=141, while capturing the VALUE gives rc=0 for a one-line producer and rc=141 for a many-line one -- BUT WITH THE CORRECT VALUE EITHER WAY (`seq 1 200000 | head -n 1` yields `1` at rc=141). So SIGPIPE lands in the pipeline's EXIT STATUS and never in what it printed. That is exactly why the repository's own uses are not exposed: `backup_scheduled.sh:140,189` and `check_backup_age.sh:199-200` all pipe into `head -n 1` inside a command substitution, then test the resulting VALUE and never the pipeline's status. The fix in the harness was to capture first and match second, which is the same discipline.

SECOND, and the same direction: two test floors were set ABOVE the observed count -- 16 against 15 assertions, and 12 against 11 -- so a fully passing run reported FLOOR NOT MET. That is the precise mistake the CI notes warn about when they say the dangerous direction for the 300 s and 180 s timeouts is DOWN, made in the same session that documents it. A floor belongs at or below what was observed while building it: at the observed count for a deletion detector, well below it for a collapse detector, and NEVER above.

The reading was then acted on. It said shell scripts were stored CRLF in the index and would therefore break on the Pi, a `.gitattributes` pin was written to fix that, and it was COMMITTED. Counting actual `\r` bytes showed every file is already LF in the index, because `core.autocrlf=true` normalizes on commit; the commit fixed nothing and was reverted before the push.

The distinction worth keeping: AN EMPTY RESULT IS AT LEAST SUSPICIOUS. A plausible number is not, and it invites the next step rather than a second look. The other thirteen are caught by asking "did this actually check anything"; this one is only caught by asking "is this number measuring what I think it is", which nobody asks of a number that already agrees with the hypothesis. It also passed a cross-check and won: a correct `cat -A` reading on the same file showed no `^M` and was overridden by the confident wrong number.

Stderr going somewhere nobody is looking does not count as reporting, and neither does `2>/dev/null`.

## Rules
- All code comments in English
- No emojis in code or comments
- I am a beginner, briefly explain what you are doing and why
- `.claude/skills/execution-discipline/SKILL.md` carries the execution discipline for this repository and applies to every task that changes a file, including the rule on staying inside the current task's scope
- After every change, update ARCHITECTURE.md. One line per new or changed item. No explanations beyond what is already there — just add or update the relevant entry. Never let it grow into prose.
- A change that makes existing documentation false must correct it in the same commit or the same batch, even when that falls outside the stated scope. This covers ARCHITECTURE.md, CLAUDE.md and the CI notes. Scope boundaries exist to prevent creep, not to preserve known-false text.
- A step that watches for a condition reports its own failure. A broken checker and a checker that found nothing produce identical output, and the identical output is the reassuring one, which is why every gate here asserts on a count. The INVERSE is a separate defect and is not the same rule: a check that reds on correct work teaches people to ignore red. See the nineteenth occurrence under Local Tooling, kept distinct from the other eighteen for exactly that reason.
