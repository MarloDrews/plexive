## Workflows, triggers and which three are gates

`android-build` ran one `assembleDebug` and nothing else until 2026-08-30. The Kotlin test source set was wired and never run, and the AGP lint task was registered by its plugin and never called; both are a check installed and never wired to anything that runs it. One Gradle invocation now runs `:androidApp:assembleDebug :shared:testAndroidHostTest :androidApp:lintDebug` -- one configuration phase, one daemon, one `--console=plain` log, which is also what keeps the comment in `dependency-submission.yml` about this job parsing only its own log true. The counts and their kinds are under "## The floors in `android-build.yml`".

The workflow uses `distribution: corretto` because `mobile-kmp/gradle/gradle-daemon-jvm.properties` pins `toolchainVendor=AMAZON`. Any other vendor makes Gradle ignore the installed JDK and download Corretto from foojay on every run. Changing that line means changing `.github/workflows/android-build.yml` too.

The `push` trigger is scoped to `branches: [main]` on purpose. Unscoped, it also fires on the branch behind a pull request, so one commit gets two runs reporting the same `android-build` check name and the required check resolves to whichever finishes last. Do not widen it to make branches build; branches build through their pull request. Keeping `main` is what seeds the Gradle dependency cache, since `setup-gradle` only writes the cache from the default branch, and a cold run takes about 3m25s against about 40s warm.

There are five workflow files. Three are gates, one per codebase, one job each: `android-build.yml`, `backend-checks.yml`, `frontend-checks.yml`. One job per codebase on purpose. The number of check names a person has to interpret on a pull request is the real budget, and three is what it will bear.

`codeql.yml` and `dependency-submission.yml` are the other two, and neither is a gate. Both are deliberately absent from the ruleset, so the required checks are still exactly those three, and they are the reason the sentence above says "three gates" rather than "three workflows".

## CodeQL and dependency submission

`codeql.yml` breaks one of the patterns below on purpose: it runs a matrix, so it contributes two check names, `codeql (python)` and `codeql (javascript-typescript)`, neither of which is required. Its languages are `python` and `javascript-typescript`; `java-kotlin` is excluded because CodeQL cannot analyse Kotlin without a build -- `build-mode: none` is supported for Java and explicitly not for Kotlin, where it skips the code and emits a warning -- so covering `mobile-kmp/` would mean a second real Gradle build alongside `android-build.yml`. That is a separate decision, not an oversight.

It gained `push: branches: [main]` on 2026-08-27, so its triggers are now push-on-main plus `schedule:` plus `pull_request:`. This matters because code scanning tracks alerts against the DEFAULT BRANCH: the Security tab is populated by runs on `main`, and a pull request run reports on that pull request alone. Before the push trigger the baseline came from the weekly schedule alone, so a merge did not refresh the Security tab and the baseline could be up to a week stale. That was traded for one extra run per merge, deliberately and on the user's instruction, because Actions minutes are unmetered on a public repository and a stale baseline is the more expensive of the two. The schedule stays, but its job has changed: it is no longer what establishes the baseline, it is what keeps the analysis fresh against newly published CodeQL queries during a week with no merges.

Adding it also silenced a warning worth recording, because it will not appear again and someone reading old logs will meet it. While there was no `push:` trigger, `codeql-action/init` emitted `##[warning]1 issue was detected with this workflow: Please specify an on.push hook to analyze and see code scanning alerts from the default branch on the Security tab.` on EVERY run, once per matrix leg. It was a static lint on the workflow file, not a report that anything failed, and it was wrong in the narrow sense that scheduled runs did execute on `main` and their analyses were default-branch analyses. The real gap it pointed at was the latency described above.

`dependency-submission.yml` is the fifth, added 2026-08-27, and it runs `gradle/actions/dependency-submission@v4` over `mobile-kmp/` to close the Gradle dependency-graph gap described under Repository Security Settings. It is a separate workflow rather than a step in `android-build.yml`, for three reasons in order of weight. Permissions: submitting a snapshot needs `contents: write`, and folding it into `android-build` would hand write scope to the job that builds unreviewed pull request code, which runs `contents: read` today. Triggers: a snapshot describes the DEFAULT BRANCH, so this must run on `main` only, while `android-build` must run on pull requests; one file cannot hold both without one of them firing where it should not. Cost: the action runs its own Gradle invocation, and inside `android-build` that time would land on a required check, whereas a separate workflow runs in parallel and slows the gate by nothing. It also leaves `android-build`'s compile-task assertion alone, which parses that job's own `--console=plain` log and would otherwise have a second Gradle run's output to contend with. It never runs on `pull_request`, so it contributes no check name to any pull request, which is the strongest form of "not a gate" available.

First run on `main` under the new `push:` trigger, 2026-08-27, on the merge that added the trigger: 87 rules and 0 results for `javascript-typescript`, 43 rules and **1** result for `python`. That one result is the first entry the Security tab has ever had: `py/clear-text-logging-sensitive-data`, high, at `backend/seed.py:239`, where the seed script prints a generated admin password to stdout when `SEED_ADMIN_PASSWORD` is unset. It was deliberate code -- the message it printed said "Save this now" -- so it was a triage decision rather than a bug report. It was ACTED ON on 2026-08-28, and the finding is now the Security tab's only cleared entry. The measurement, put next to the claim: the push run on `main` for that merge (2c1bb53) reported `python` 43 rules and **0** results, against 43 rules and 1 result on the preceding main run (41bbd76); the alert moved to `fixed` at 2026-08-27T22:24:19Z and open code-scanning alerts are now 0. The RULE COUNT is the load-bearing half of that. 43 is the same count the run carried when it reported the finding, so the zero is those same 43 rules finding nothing rather than a smaller suite asking a smaller question -- which is the difference between a real result and a vacuous pass, and the same reason the first-run note above quotes its rule counts at all.

What was wrong with it was the destination, not the intent: an operator on a fresh database has to learn the password somehow, but stdout is redirected often enough (`| tee`, `> seed.log`, a scrollback that outlives the terminal) that the value landed in a file on disk. There is therefore NO channel where the script reveals a generated secret and the tab still reads zero, and that is the scanner being right rather than being awkward: a generated secret has to go somewhere, and every somewhere is a copy in a place it should not be. So the script stopped generating and started asking. When `SEED_ADMIN_PASSWORD` is unset it reads one with `getpass.getpass()` plus a confirm entry, which does not echo; the cause is gone rather than the output moved, and there is nothing left to disclose. The no-terminal branch was also moved AHEAD of the reveal, which is a real bug the finding happened to expose: the `sys.stdin.isatty()` check used to sit after the print, so a non-interactive run disclosed the password and only then refused to continue. Nothing calls the script non-interactively -- `docs/SERVER.md:127` is a by-hand `sudo env ... python seed.py` whose env file already carries the variable, `tools/run_pipeline.{sh,ps1}` only echoed the command as an instruction to the human, and those two files left this repository on 2026-08-29, and `backend-checks.yml` only byte-compiles it -- so this broke no caller.

Worth recording because it is the argument for the push trigger, made by the trigger itself on its first run: the pull request run on the SAME commit reported 43 rules and 0 results for `python`, so the pull request leg did not surface this and the scheduled run would not have surfaced it for up to a week. The difference is scope, not luck -- a pull request analysis reports against that pull request, a default-branch analysis establishes the baseline -- and this is exactly the staleness the trigger was added to remove.

## Conventions every job follows

No workflow has a `paths:` filter. A workflow skipped by a top-level `paths:` filter reports no status at all, and a required check that never reports blocks the pull request permanently. Actions minutes are unmetered here, so the saving would buy nothing anyway.

Every job sets `shell: bash` explicitly. The Linux default is `bash -e {0}`, without `pipefail`, which is how a piped failure becomes a green check; `shell: bash` is `bash --noprofile --norc -eo pipefail {0}`. This already bit the Android workflow once.

Every check asserts on a count, not only on an exit code, because all of them can pass having checked nothing: a loop that globs no files exits 0, `compileall` over a wrong path exits 0, `npm test` with no matching files exits 0 reporting `pass 0`. THE COUNTS ARE OF FOUR KINDS AND THE NUMBER DOES NOT SAY WHICH, so each one has to say which it is where it is written, and making them uniform is the mistake. COLLAPSE DETECTORS sit well BELOW the observed count and catch the paths moving or the tool checking nothing, so ordinary work never reaches them: the backend Python file count (60 against 82 observed), ruff (60 against 82), mypy (60 against 82), the schema ledger's two (2 revision files against 2, and 10 tables against 13), the frontend `MIN_FILES` (150 against 246) and `MIN_A11Y_RULES` (6 against 6 shipped by `eslint-config-next`). DELETION DETECTORS sit EXACTLY on the observed count so a removal has to be a deliberate edit here: the 64 backend pins, the 16 backend suite files and the 1 file under `.claude/rules/`. RATCHETS fail when a number goes UP, have no lower bound and no equality check at all, and never come down except by hand in the same commit as the batch that fixes findings. THERE ARE FOUR OF THEM AND THIS IS THE ONLY PLACE THAT LISTS THEM, because three separate batches each wrote a paragraph calling its own the first or the only one: `MAX_ERRORS=88` (ESLint) in `frontend-checks.yml`, `MAX_LINT_FINDINGS=3` (AGP lint) in `android-build.yml`, and `MAX_RUFF_FINDINGS=37` (ruff E4,E7,E9,F) and `MAX_MYPY_ERRORS=201` in `backend-checks.yml`. The frontend test floor of 40 reads like a deletion detector and is not one: 56 tests pass against it (64 declared, 8 gold tests skipped, measured 2026-08-29), so it catches the runner matching no files rather than a test being deleted. The per-file pairings are under "## The count floors and the two ratchets in `backend-checks.yml`", "## The three count floors in `frontend-checks.yml`" and "## The floors in `android-build.yml`", and the fourth kind is under "## The surface budget, the fourth kind of count".

## The backend suite loop and the `battle_test.py` hangs

The backend suites run as a per-file subprocess loop, not `pytest tests`. 12 of the 16 suites execute their whole body at import and share one app instance, one in-memory rate limiter and the first module's temp SQLite file, so in one process they collide: pytest collects 92 of about 979 assertions and interrupts on 4 collection errors. The loop also runs every suite after one fails, so a second failure is not hidden behind the first.

The `backend-checks` suite loop hung three times, every time on `battle_test.py`, all three on 2026-08-27, and every time on a commit that touched no backend code. It is DIAGNOSED AND FIXED as of 2026-08-27; the cause was the test harness and not the server, and several of the notes below used to say the opposite. They are corrected in place rather than deleted, because the wrong inferences are the useful part of the record. Full workings: `docs/research/battle-hang-diagnosis-2026-08.md`.

One earlier observation is retired outright: "three for three it has also come straight after `arena_test.py` passed" carries no signal whatsoever. The suites run as separate processes over an alphabetical glob, so `arena_test.py` precedes `battle_test.py` in every single run, including the 22 that passed.

First: `arena_test.py` passed, `battle_test.py` then produced no output for 19 minutes, and the commit had touched one line of ARCHITECTURE.md. The run was cancelled by hand and re-run unchanged, and `battle_test.py` passed in 2.681 s. Second: same suite, again straight after `arena_test.py` passed, on a commit touching ARCHITECTURE.md and `frontend/package.json`. This time the `timeout 300s` added after the first occurrence fired at 300.005 s, so the job went red by itself and the summary table still printed and named the suite. Re-run unchanged, `battle_test.py` passed in 2.826 s. Two for two, the failure does not reproduce.

Third: on Dependabot pull request #39, whose entire diff was three lines of `mobile/package-lock.json` and which therefore cannot have touched anything the backend runs. `arena_test.py` passed, `battle_test.py` timed out at 302.297 s, the remaining 13 suites all passed, and a re-run of the job unchanged went green. The instrumentation added after the second occurrence fired exactly as designed and produced the stack.

Rate, so the count is not read as a frequency: 25 runs of this workflow, 3 of them hangs. Note that the second and third are invisible in the Actions run list, because re-running a job overwrites the run's conclusion and it now reads `success`; the evidence is the log of the first attempt, not the run's status.

THE THIRD OCCURRENCE NARROWED IT, and this is the first thing about the cause that is not a guess. The faulthandler dump puts the main thread here:

```
Current thread (most recent call first):
  threading.py line 359 in wait
  concurrent/futures/_base.py line 455 in result
  anyio/from_thread.py line 334 in call
  starlette/testclient.py line 185 in receive
  starlette/testclient.py line 198 in receive_json
  backend/tests/battle_test.py line 124 in <module>
```

Every other thread is idle: two `anyio` worker threads parked in `queue.get`, three portal event loops parked in `selectors.select`. Nothing is spinning and nothing is deadlocked on a lock. The suite is simply blocked forever waiting for a WebSocket frame that never arrives.

`battle_test.py:124` is `fin_a = ws_a.receive_json()`, in the "both finish frames end the room" section that freezes ARCH-004. The sequence is: alice sends `finish`, bob receives `opponent_finish` (line 121, which had already passed), bob sends `finish`, and alice never receives hers.

THE INFERENCE DRAWN FROM THAT WAS WRONG, and this is the correction. The note here used to say that the second `finish` is sometimes not relayed to the player who finished first, blamed "a race between the first `finish` tearing the room down and the second one looking for somebody to relay to", called it a lead pointing at the M142 finish/teardown path, and moved the state machine from not implicated to implicated. The line number and the dump were right. Everything read off them was not. THE STATE MACHINE GOES BACK TO NOT IMPLICATED, on evidence rather than on absence of evidence: `battle.py:220-221` captures both the recipient and the battle id BEFORE the teardown pops at `:222-225`, inside the same single lock acquisition, and `manager.send` resolves the socket from `_sockets`, which `_teardown_room` never touches. There is no window in which the second `finish` loses its recipient. Driving the same app over in-process ASGI websockets on ONE event loop ran 500/500 clean, including the stale branch and back-to-back finishes, which bounds the server-side failure rate below roughly 6 in 1000.

The cause was the harness. `battle_test.py:34` constructed `TestClient(app)` and never entered it, and starlette only shares one portal when the client is entered, so EVERY `websocket_connect` got its own portal, its own event loop and its own thread -- those are the "three portal event loops parked in `selectors.select`" the dump itself reported. Bob's relay then ran on bob's loop and wrote into a stream owned by alice's loop, and anyio wakes that receiver through `loop.call_soon`, which unlike `call_soon_threadsafe` does not write the target loop's self-pipe. With alice's loop already parked in `select(None)` the frame is delivered and the loop is never woken. Not a lost message: a lost wakeup. Measured at 1 hang in 200 locally and 3 in 200 on the CI-pinned set, and made deterministic by delaying the second relay 50 ms (5/5 hangs, 0/30 after the fix). READ THOSE TWO NATURAL RATES AS SINGLE SAMPLES OF A RATE THAT MOVES WITH MACHINE LOAD, not as properties of the code: a later session on the same local set hit a natural hang on the third run of its first five, which is 1 in 5 rather than 1 in 200. The forced case is the measurement; the natural rates only establish that the window is small, real and variable, and CI's own 3-in-25 is a third sample from a third machine. The fix is one line, `stack.enter_context(client)`, and the same line in `chat_test.py`, which was exposed identically and hangs under the same forced delay at its own cross-loop read (`chat_test.py:154`). See the DEPLOYMENT INVARIANT section of ARCHITECTURE.md for the general rule this violated.

Starlette moved 1.2.1 -> 1.3.1 between the first two occurrences, and it is now CLEARED rather than merely unimplicated: the race reproduces on both, 3 hangs in 200 runs on the CI-pinned 1.3.1 and 1 in 200 on the local set, and the forced 50 ms repro hangs 5/5 on each. One caveat kept honest: the local environment is starlette 1.2.0, not the 1.2.1 named above, so 1.2.1 itself was never run. The versions either side of it behave identically, which is why this is stated as cleared. The `StarletteDeprecationWarning` about `httpx` is not a lead either, it is emitted at import on every run under 1.3.1 including passing ones, and is simply the last thing printed before the dump.

The re-run policy is inverted by the fix, so it is restated here rather than deleted. Re-running a red `battle_test.py` unchanged was the CORRECT response while the cause was unknown, unreproducible and believed to be in the server: the suite genuinely passed on the retry, and a merge could not wait on a fault nobody could reproduce. It is the WRONG response now. The known cause is gone, so a fresh hang or a red `battle_test.py` is a new fact and must be read, not retried -- and retrying actively destroys the evidence, since re-running a job overwrites the run's conclusion, which is exactly why the second and third occurrences are invisible in the Actions run list. Read the log of the first attempt: the suite now carries its own watchdog and prints a stack before it dies.

## Timeouts, watchdogs and where their numbers come from

Each suite therefore runs under `timeout 300s`, and the job carries `timeout-minutes: 20`. THE DERIVATION OF THAT 300 s CHANGED ON 2026-08-28 AND IS RESTATED RATHER THAN LEFT DANGLING, because a constant whose stated reasoning names a deleted file is how the next person talks themselves into changing it. It was about 2.3x `thumbnails_test.py`'s 130 s, the slowest healthy suite; that suite left with the thumbnail render subsystem, the slowest healthy suite is now `arena_test.py` at about 29 s in CI, and 300 s is therefore about 10x rather than 2.3x. The 180 s watchdog below went from about 1.4x to about 6x the same figure. NEITHER IS LOWERED. Both exist to bound an unbounded hang rather than to bracket a slow run, so a larger multiple costs nothing and buys margin on a shared runner. The dangerous direction is down: a per-suite timeout that fires on a slow-but-healthy run converts a reliable gate into an unreliable one, which is the fastest way to get a gate switched off, and hosted runner speed is not ours to control. `timeout-minutes: 20` is the backstop for a hang outside the loop, in `pip install` or the boot check. It is about 5x the observed job duration, and it is deliberately loose enough that a suite can burn its full 300 s and the summary table still prints, because a job killed by `timeout-minutes` prints nothing and that table is the only thing that names the suite that hung.

The summary reports four statuses, not two, and the loop runs every remaining suite after any of them. `TIMEOUT` counts as a failure but is not reported as `FAIL`, because the two mean different things and the distinction is the only thing that makes a second occurrence recognisable as a pattern. `KILLED` splits the same way again: `timeout --kill-after` sends SIGKILL, but so does the kernel OOM killer, and both arrive as exit 137. Exit 137 is therefore read as a timeout only when the elapsed time is at least 90 percent of the limit, since `timeout` cannot fire before its own limit; below that it is `KILLED`, cause unknown, with OOM the likely one. The named candidate used to be `thumbnails_test.py`, which was image-heavy; it left on 2026-08-28 and no remaining suite is an obvious OOM risk, so this branch now flags a cause nobody has a suspect for, which is more reason to keep it distinct rather than less. Each suite's name is also printed before it is invoked, because its output is redirected to a file and dumped only on failure: without that line a hang leaves the live log completely silent, which is why the first 2026-08-27 hang could only be attributed to a suite by cancelling the run. The second one was attributed from the summary table without touching the run, so this part is load-bearing and is doing its job.

`battle_test.py`, `chat_test.py` and `arena_test.py` additionally carry their OWN 180 s watchdog, a `threading.Timer` that announces itself in one line, dumps every thread's stack and exits 1. This changes what a hang in those three looks like, deliberately: it self-terminates at 180 s and lands in the `FAIL` branch, NOT in `TIMEOUT` at 300 s. A stack is worth more than a label, and the announcement line is what makes the lost label harmless, since it says in the log that the suite hung rather than that a check failed. THE USEFUL HALF IS THE INVERSE: after this change, a 300 s `TIMEOUT` on battle, chat or arena means THE WATCHDOG ITSELF DID NOT FIRE -- a hang before its timer started, a wedged interpreter, a process that outlived `os._exit` -- which is a rarer and stranger event than a `FAIL`, and nobody would guess that without being told. The other 13 suites are untouched and still report `TIMEOUT` in the ordinary way.

The watchdog was proved rather than assumed, 2026-08-27, by dropping a frame the suite waits on (measured at 90 s, before the limit was raised to 180 s; only the number changed): the timer fired at 90 s (94 s wall clock), the exit code was 1 so the loop counts it as a failure rather than a pass, the announcement and a full all-thread stack naming the parked line both reached the log, and the 20 `ok:` lines printed before the hang were still there. That last one is the whole reason `flush=True` sits on the announcement: `os._exit` skips every cleanup path, and CI redirects each suite to a file where stdout is block-buffered, so without it the log would show a stack and nothing else. A healthy run under the same redirection prints nothing extra.

Where the 180 s comes from, since a bare number invites someone to trim it. THE BINDING CONSTRAINT IS LOCAL FALSE POSITIVES, NOT CI COST. In CI this watchdog earns very little: `timeout --signal=ABRT 300s` under `-X faulthandler` already produces the same all-thread stack, so all the watchdog does there is make it arrive sooner, and a hang burning 180 s instead of 90 s out of a 300 s per-suite budget and a 20-minute job ceiling is negligible. Its unique value is LOCAL, where none of that instrumentation runs -- and local is exactly where the margin is thin. 180 s is about 5.7x the worst healthy run measured: 31.5 s on a 12-core laptop deliberately oversubscribed with 12 concurrent test processes, against ~2.7 s for the same suite in CI. It was 90 s for one commit, which was only 2.9x that worst healthy run; raising it is strictly better on the axis that matters and irrelevant on the one that does not. The dangerous direction is DOWN, the same as for the 300 s: a watchdog that fires on a slow-but-healthy run is the same mistake as a per-suite timeout that does, and the diagnosis session made exactly that mistake once with a 20 s watchdog before raising it.

Every suite runs as `python -X faulthandler` and is aborted with `timeout --signal=ABRT`, not the default `SIGTERM`, so that a hang leaves a stack rather than silence. This was measured on the runner rather than assumed, in both directions. `-X faulthandler` only dumps on a FATAL signal, which is SIGSEGV/SIGFPE/SIGABRT/SIGBUS/SIGILL and NOT SIGTERM: with SIGTERM the flag prints nothing at all, so the signal had to change too, and the flag alone would have been a no-op that looked like a fix. The exit code does not change, because GNU `timeout` reports 124 for a timeout whatever signal it sent unless `--preserve-status`, so the classification above is untouched and the 137 branch still catches a suite that outlives ABRT. A timed-out suite now has its FULL log printed instead of the last 40 lines, because the dump is the evidence and tailing it would throw away the top of it.

The rejected alternative was `faulthandler.register(SIGTERM)` from a `sitecustomize.py` on `PYTHONPATH`, which needs no signal change and touches no test file. It dumps, but `register()` does not terminate, so the suite outlived its own dump and `--kill-after` SIGKILLed it: exit 137, landing in the `KILLED` branch that exists to flag a suspected OOM. Buying a traceback by making a timeout indistinguishable from an OOM is a bad trade. One cosmetic side effect remains: `timeout` prints `the monitored command dumped core`, and because `/proc/sys/kernel/core_pattern` pipes to `systemd-coredump` the kernel ignores `RLIMIT_CORE`, so a core is handed to systemd. Nothing is written into the workspace and the runner is ephemeral, so this costs nothing; `ulimit -c 0` is set anyway.

## Taking a before-number

A BEFORE-NUMBER IS TAKEN BEFORE THE TREE IS TOUCHED, AND THE TREE MUST BE UNCHANGED FOR THE WHOLE TIME IT IS BEING MEASURED. This is a measurement rule, not a CI rule, and it sits here with the others because it is the same failure class. It was learned on 2026-08-28, during the thumbnail-removal batch: the backend suite loop was started to capture the before wall clock, and an edit deleting two classes from `app/schemas.py` landed while `thumbnails_test.py` was still running. That suite imports one of them, so it exited 1 after 131.3 s, and the total would have been reported as 267 s. Re-measured on a restored tree it was 130.3 s and exit 0, for a true baseline of 266.0 s.

What makes it worth a rule rather than a note is the SHAPE. The measurement did not error, the loop did not stop, and the number it produced was a plausible one -- 131.3 s against a true 130.3 s, well inside the noise anyone would accept. It was only caught because the exit code was checked as well as the duration, and the suite that changed was the one being timed. Had the edit hit a suite whose import it did not break, or had only the total been recorded, the wrong number would have been carried into the report and into the CI notes as fact. A measurement taken against a tree that is being edited is a checker that watches for a condition and reports its own failure as a result, which is the `## Rules` entry in a form the other thirteen instances do not cover: the tool was fine, the question was right, and the SUBJECT changed underneath it.

So: take every before-number first, in one pass, and do not begin editing until it has finished. Where that is impractical, record what the tree was at (`git rev-parse HEAD` plus a clean `git status --porcelain`) at both ends of the measurement and say so next to the number.

## Route counts, pinning and mirroring production

The backend boot check counts `app.openapi()["paths"]`, not `len(app.routes)`. The route count is not a property of this codebase, it is a property of the installed FastAPI version: on the same commit it was 57 on the dev laptop (0.136.3, one flattened `APIRoute` per endpoint) and 23 in CI (0.141.1, where `include_router` leaves one `_IncludedRouter` per router). While `requirements.txt` pinned nothing, both were "correct" on the same day. The OpenAPI path count was 45 on both, so that is what the guard asserts. IT IS 42 NOW, NOT 45: the three `/api/thumbnails/*` endpoints left with the render subsystem on 2026-08-28, and this paragraph went on claiming 45 afterwards. Measured again 2026-08-28 during the schema reconciliation: 42. The guard is a FLOOR of 20 rather than an equality, which is why the drift never reddened anything -- and why nothing caught the sentence either. Pinning fastapi has since made the route count stable too, and that is not a reason to switch back: the path count describes the API, the route count describes how the installed FastAPI represents it internally. Pinning made the bad measure stable, not correct.

## The surface budget, the fourth kind of count

`tools/surface-budget.json` holds one CEILING per governance container and the surface budget step in `backend-checks.yml` reads it. It sits in that job for the same reason the `.claude/rules/` check does -- it is the only one of the three with a Python interpreter on PATH by design -- and immediately after it, before `Install dependencies`, so a malformed budget file reds in seconds rather than after the suites.

A CEILING IS NOT A RATCHET AND MUST NOT BE ADDED TO THE FOUR-RATCHET LIST. Both fail when a number goes up, and there the resemblance stops. A ratchet tracks a DEFECT count that ought to reach zero: `MAX_RUFF_FINDINGS` going to 0 is the goal, and the number comes down as findings are fixed. A ceiling tracks a STRUCTURAL SIZE that must not reach zero: `workflow_files` at 0 would delete CI, `hook_scripts` at 0 would delete the hooks. The number comes down only when somebody deliberately removes a container member. Ratchets and ceilings are counted separately for that reason, and the list of four ratchets is still four.

THE NUMBERS CAME FROM A REPLAY, NOT FROM JUDGEMENT. 754 first-parent commits (2026-05-30 to 2026-08-31) were measured, every increase in every container was classified as one that should or should not have been blocked, and each ceiling sits at or above the largest legitimate one. The commit that set each number is named in that container's `why` field, which is why the file is JSON with a prose field rather than a list of numbers. The workings: `plexive-docs/research/surface-budget-2026-08-31.md`.

The replay produced two kinds, and the split is the useful part:

- **PINNED, 15 of the 23.** Growth is a discrete deliberate act and no historical commit ever took the count above where it stands, so the pin blocked nothing that should not have been blocked. `claude_md_sections` at 10, `claude_md_rules`'s neighbours in the settings file, `hook_scripts` at 3, `project_skills` at 2, `workflow_files` at 5, `workflow_jobs` at 5, and the five zeros -- `settings_permissions_ask`, `project_commands`, `project_subagents`, `project_plugins`, `project_mcp_servers`. The five zeros record decisions this topic actually made: a skill, a plugin, a subagent, an MCP server and a hook were each considered and declined. A pin costs one line in the budget file, in the same commit as the growth. That cost is the feature.
- **HEADROOM, 8 of the 23.** A standing rule makes growth of that shape RECUR, so a pin would red on work somebody is required to do. The headroom is the size of the largest legitimate single commit, never a round number. `claude_md_bytes` +2809 and `claude_md_lines` +36 are both set by `f2f49f95`, which recorded the exact commands the three checks run because the same-batch documentation rule required it. `workflow_steps` +5 is set by `7d2a0c0c`. `correct_work_cases` +10 is set by the same merge and the ceiling is carried at that width above the measured count, which is why storing fifteen cases at once on 2026-08-31 raised it in the same commit rather than redding a later one. `workflow_named_thresholds` +1 is set by `8261e3a`, and that number is COUNTED BY NAME rather than by assignment since 2026-08-31: the shape regex counted `NAME=value` and the `NAME="$NAME" python3 -` line that carries it into a heredoc as two thresholds, which made ten matching lines in `backend-checks.yml` read as ten and not as the seven that exist. The by-name replay gives 0 -> 11 at the merge that created them all, then +1, then +1, so the headroom is one.

`claude_md_bytes` AND `claude_md_lines` ARE A BACKSTOP AGAINST SILENT DOUBLING, NOT A FENCE, and the file says so in its own `why` fields. They do not stop a drip of individually defensible paragraphs, which is exactly how `CLAUDE.md` refilled from 17,758 bytes to 25,422 in the two days after the shrink. The fence is the three semantic counts -- `claude_md_sections`, `claude_md_rules`, `claude_md_unconditional_rules` -- because prose corrections cannot move them and only a deliberate addition can. `correct_work_cases` is the weakest of the eight by a distance: 10 of headroom on a container of 27 catches a generator dumping cases and catches nothing else, and it is kept anyway because a container that is measured is one somebody can see move.

A RULE IS AN OPENING LINE, and that definition is written beside the metric in `tools/surface-budget.json` rather than left inside the parser. A top-level `- ` bullet at column 0 opens a rule; so does the first line of a blank-line-separated paragraph at column 0; continuation lines and indented sub-bullets belong to the rule above them. The first version counted bullets plus paragraph-runs, which made REFORMATTING move the number: measured 2026-08-31, rewrapping two of the six bullets at 98 columns read 9 against a ceiling of 8 and rewrapping all six read 11, with no rule added and not one character of text changed. That is the inverse defect this repository keeps apart from the rest -- the accompanying line was available, was one character, and would have recorded a rule that does not exist. Stored as `cw-9a` through `cw-9d`. ONE SHAPE IS STILL COUNTED WRONG AND IS PINNED RATHER THAN FIXED: a continuation line that itself begins `- ` is indistinguishable from a bullet, to this parser and to a markdown reader both, so `cw-9e` declares the exit code it produces today and reports a flip in either direction.
